# System Architecture

**Last updated:** 8 November 2026

## 1. Overview

The Autonomous Multi-Agent Decision Twin for Dynamic Packaging Scheduling is a software-based system that receives customer orders, generates scheduling proposals, evaluates candidate schedules and simulates execution of a selected schedule.

The system consists of:

- Three React frontend applications.
- One planned central FastAPI backend.
- One shared Cloud Firestore database.
- Three independent scheduling agents.
- One Main Agent responsible for final scheduling decisions.
- A two-line Digital Twin.
- A two-line Production Model.
- Four independent CoppeliaSim scenes.
- A local Python communication layer for CoppeliaSim.

The three frontend applications have been developed and deployed to Firebase Hosting. Their backend integration is still pending.

### 2.4 FastAPI Backend

### 2.5 Scheduling Agents

Three independent agents generate scheduling proposals:

- Rule-Based Agent: deterministic scheduling logic.
- Machine Learning Agent: ML-based scheduling proposal.
- Reinforcement Learning Agent: RL-based scheduling proposal.

Teammate 2 also implements five conventional baselines:

- FIFO
- EDD
- SJF
- Priority Orders First
- Least Slack Time First

The baseline algorithms are used for comparison and evaluation.

Each agent should produce its own independent proposal. The proposals must not be merged into a hybrid schedule.

The common proposal envelope and exact field names are still subject to final shared-contract approval.

### 2.6 Main Agent

The Main Agent, owned by Teammate 4, is the scheduling decision authority.

Its responsibilities include:

- Receiving and validating independent agent proposals.
- Checking proposal and system-state consistency.
- Handling invalid proposals and agent failures.
- Requesting Digital Twin evaluation.
- Comparing evaluated proposals.
- Selecting one complete proposal.
- Recording decision logs, explanations and rejected-proposal reasons.
- Producing the final schedule for Production execution.

The Main Agent is an importable Python package. It must not connect directly to CoppeliaSim or write directly to Firestore.

The proposed common proposal representation uses an order sequence. The current shared contract still requires confirmation of the exact structure, including the distinction between a flat schedule list and `schedule.order_sequence`.

The current T1 integration approach is for the Main Agent to own order-to-line allocation. Individual scheduling agents should not independently assign orders to physical lines. The agreed allocation must be consistent across proposals before Digital Twin evaluation. The final shared interface requires confirmation with T4 and T3.

### 2.7 Digital Twin Simulation

The Digital Twin is owned by Teammate 1.

It evaluates candidate schedules and returns measured simulation information to the Main Agent.

The Digital Twin does not select a winning proposal, rank proposals or combine independent agent proposals.

The implemented Digital Twin contains two independent packaging-line scenes:

- Digital Twin Line A.
- Digital Twin Line B.

Implemented functionality includes:

- Python-to-CoppeliaSim ZeroMQ communication.
- Independent line controllers.
- Product dispensing for P1–P4.
- Inventory tracking.
- Two-box conveyor movement and handoff.
- Sequential order execution.
- Independent line execution.
- Candidate schedule evaluation.
- State management for individual scenes.
- Concurrent evaluation of Line A and Line B for one candidate.
- Sequential evaluation of different candidates.
- Scene reset and restoration after candidate evaluation.

The parameter generator provides reproducible parameter candidates. It is not a fourth scheduling agent and does not replace the three independent agents.

The current implementation does not yet integrate T5's machine-health calculations or a validated time-dependent machine-wear model.

#### Digital Twin evaluation behaviour

For each candidate:

1. Both line schedules are validated.
2. The two line evaluations execute concurrently.
3. Each line uses its own ScheduleEvaluator and CoppeliaSim scene.
4. The candidate execution results are recorded.
5. Each evaluated scene is restored to its initial state.
6. The result is returned to the caller.

Different candidate proposals are evaluated sequentially. The Main Agent retains selection authority.

### 2.8 Production Model

The Production Model is owned by Teammate 1.

It contains two independent packaging-line scenes:

- Production Line A.
- Production Line B.

The Production Coordinator accepts a Main-Agent-selected production plan and executes its two line schedules concurrently.

Implemented functionality includes:

- Separate Production Line A and Line B scenes.
- Independent Python connections.
- Product dispensing and box movement.
- Two-box handoff.
- Persistent inventory across plan executions within the same running Python process.
- Pre-execution validation of both line schedules.
- Concurrent execution of the two production lines.
- Requested and effective parameter reporting.
- Deterministic production parameter variation.
- Failure reporting and line blocking when manual recovery is required.
- Combined production metrics based on parallel execution time.

The default production variation policy uses a deterministic seed of 2026 and a maximum relative variation of 2%. These are configurable demonstration assumptions, not validated industrial measurements.

Production variation does not constitute machine-health degradation.

The Production Model executes only the selected production plan. It does not select agent proposals or perform Main Agent decision-making.

### 2.9 Production Comparison

The T1 Production Comparator compares Digital Twin predictions with actual Production Model execution reports for the same schedule.

It compares:

- Order assignments and product quantities.
- Total orders and total balls.
- Completion time.
- Average order completion time.
- Orders per minute.
- Balls per minute.
- Combined two-line makespan and throughput.

The comparator reports differences. It does not introduce unapproved deviation thresholds, select proposals or determine the Main Agent's winning plan.

Machine-health and wear comparisons are not included yet.

## 3. High-level data flow

The intended end-to-end workflow is:

1. A customer submits an order through the Customer Website.
2. The FastAPI backend validates the order and creates a unique Order ID.
3. The order is stored in Firestore and enters the scheduling process.
4. The Rule-Based, ML and RL agents independently generate scheduling proposals.
5. The Main Agent receives and validates the proposals.
6. The Main Agent coordinates order-to-line allocation using the agreed policy.
7. The Main Agent requests Digital Twin evaluation of each complete proposal.
8. The Digital Twin evaluates the Line A and Line B schedules concurrently for each candidate.
9. The Digital Twin returns evaluation results.
10. The Main Agent compares the candidate results and selects one complete proposal.
11. The selected production plan is sent to the Production Coordinator.
12. The Production Coordinator executes the selected Line A and Line B schedules concurrently.
13. Production execution results are returned to the backend integration layer.
14. The backend persists relevant updates and makes them available to the websites.
15. The customer sees the order as Completed only after the actual simulated execution finishes.

The complete workflow remains an integration target. The individual T1 Digital Twin and Production components have been implemented and tested, but the end-to-end connection to the agents and backend is pending.

## 4. Machine-health data flow

The intended health-data workflow is:

1. An operator enters readings or requests a synthetic scenario through Health Controls.
2. The T5 health-data component validates and labels the input.
3. Health calculations produce derived values and classifications.
4. The backend persists the relevant health information.
5. The Digital Twin maps applicable health information internally to the corresponding equipment.
6. Candidate schedules can be evaluated using the validated simulated machine-health condition.
7. The Dashboard displays relevant health information.

Health API integration, per-line wear history and health-dependent Digital Twin behaviour are pending coordination with T5.

Line identifiers currently used by the redesigned Health Controls interface are `line_1` and `line_2`. The T1 Python simulation uses internal identifiers `line_a` and `line_b`, with scene identifiers listed in Section 5. A shared line-identifier contract and adapter must be maintained consistently.

## 5. CoppeliaSim communication

CoppeliaSim runs locally on the project owner's Windows computer.

The four independent scenes use the following ZeroMQ Remote API RPC ports:

| Scene | Scene ID | RPC port |
|---|---|---:|
| Digital Twin Line A | `digital_twin_line_a` | 23000 |
| Digital Twin Line B | `digital_twin_line_b` | 23002 |
| Production Line A | `production_line_a` | 23004 |
| Production Line B | `production_line_b` | 23006 |

Each scene has an independent Python connection.

The current Python line controllers perform direct kinematic updates through ZeroMQ while the CoppeliaSim physics simulation is stopped. The simulation Play button must not be used during these tested kinematic operations.

The completed live tests demonstrate independent scene control and concurrent Python execution. They do not establish simultaneous CoppeliaSim physics-engine execution.

The ZeroMQ RPC ports must never be exposed directly to the public internet.

A future local bridge must communicate with the cloud backend through authenticated outbound HTTPS requests or polling. The cloud backend must not directly connect to the user's local CoppeliaSim instance.

## 8. Shared integration rules

All components must use the approved shared contracts.

Integration conventions include:

- JSON-based communication.
- ISO 8601 timestamps in UTC.
- Explicit units for physical and time-related values.
- Stable IDs for orders and other entities.
- A schema version for shared payloads.
- Pydantic validation at backend boundaries.
- Documented error responses and failure handling.

The following naming differences have been identified and require final reconciliation:

- Product IDs: P1–P4 versus `ball_1`–`ball_4`.
- Quantity fields: `product_quantities` versus `items`.
- Rush deadline: `requested_deadline` versus `requested_deadline_utc`.
- Order status: customer-facing labels versus backend values.
- Proposal structure: flat schedule list versus `schedule.order_sequence`.
- Health Controls line IDs: `line_1`/`line_2` versus T1 internal `line_a`/`line_b`.

Anay's current RL response confirms that P1–P4 alignment is intended, but the complete shared proposal and order schemas are not yet frozen.

The final API and Firestore structures must be agreed by T1, T2, T3, T4 and T5 before being treated as common interfaces.

## 11. Architecture principle

The three agents independently propose schedules.

The Main Agent validates proposals, coordinates the final scheduling decision and retains selection authority.

The Digital Twin evaluates complete candidate schedules and reports operational metrics. It does not select the winner.

The Production Model executes only the plan selected by the Main Agent.

The backend remains the central application and persistence layer.

These responsibilities must remain separate throughout implementation.
