# System Architecture

## 1. Overview

The Autonomous Multi-Agent Decision Twin for Dynamic Packaging Scheduling is a software-based system that receives customer orders, generates scheduling proposals, evaluates candidate schedules and simulates execution of the selected schedule.

The architecture includes three frontend applications, one FastAPI backend, one Firestore database, three scheduling agents, one Main Agent, a Digital Twin simulation and two corresponding 3D simulation models.

## 2. Main components

### 2.1 Customer Website

The customer website allows customers to:

- Select quantities for four product types.
- Submit normal or rush orders.
- Provide a requested deadline for a rush order.
- Receive a unique Order ID.
- Track order progress.

Customer-facing order stages:

1. Order Received
2. Queued
3. Packing
4. Completed

Predicted completion time and delay information must not be exposed to customers. Actual completion time is displayed only after the order is completed.

### 2.2 Machine Health Controls

This application allows an operator to enter machine-health readings manually or generate synthetic readings and scenarios.

Data must be identified according to its source:

- Manual: entered by the operator.
- Synthetic: generated by the software.
- Calculated: derived by the system from other readings.

This project does not use physical machine sensors. Demonstration thresholds and health calculations must be configurable and documented rather than presented as approved industrial safety limits.

### 2.3 Project/Digital Twin Dashboard

The dashboard displays project activity, scheduling information, machine-health information and a 3D visualization.

The browser-based viewer uses Three.js. Its displayed state must be synchronized with the actual simulation state; prerecorded animation must not be presented as live simulation.

### 2.4 FastAPI Backend

The backend is the central API and integration layer.

Responsibilities include:

- Receiving and validating customer orders.
- Managing order status.
- Coordinating agent execution.
- Communicating with the Main Agent.
- Persisting relevant data in Firestore.
- Providing data to the three frontend applications.
- Supporting authenticated communication with the local simulation bridge.

### 2.5 Scheduling Agents

Three independent agents generate scheduling proposals:

- Rule-Based Agent: deterministic scheduling logic.
- Machine Learning Agent: ML-based scheduling proposal.
- Reinforcement Learning Agent: RL-based scheduling proposal.

Teammate 2 also implements five conventional baselines:

- FIFO
- EDD
- SJF
- Priority Orders First
- Least Slack Time First

The baseline algorithms are used for comparison and evaluation.

### 2.6 Main Agent

The Main Agent receives scheduling proposals and is responsible for the final scheduling decision.

Its responsibilities include:

- Validating proposals.
- Handling invalid proposals and agent failures.
- Evaluating candidate schedules.
- Comparing scores and decision criteria.
- Selecting the final schedule.
- Recording decision logs and explanations.

The Main Agent is an importable Python package. It receives the Digital Twin evaluator through a callback or dependency injection. It does not directly connect to CoppeliaSim or Firestore.

### 2.7 Digital Twin Simulation

The Digital Twin evaluates candidate schedules and returns evaluation information to the Main Agent.

The Main Agent, not the Digital Twin, selects the final schedule.

The Digital Twin also uses machine-health information when evaluating the simulated system. Mapping health information to equipment is handled internally; the operator interface does not require a machine-selection dropdown.

### 2.8 Production Model and Digital Twin Model

Two corresponding 3D models are maintained:

**Production Model**
- Represents the packaging line used to simulate execution of the selected schedule.
- Receives the final selected plan.
- Simulates packaging execution and completion.

**Digital Twin Model**
- Represents the corresponding packaging line used by the Digital Twin.
- Supports evaluation of candidate schedules.
- Must maintain matching geometry and layout with the Production Model.

Both are software simulations. Neither is connected to physical manufacturing equipment.

## 3. High-level data flow

1. A customer submits an order through the Customer Website.
2. The FastAPI backend validates the order and creates a unique Order ID.
3. The order is stored in Firestore and enters the scheduling process.
4. The Rule-Based, ML and RL agents generate scheduling proposals.
5. The Main Agent receives and validates the proposals.
6. The Main Agent requests candidate-schedule evaluation through the Digital Twin evaluator.
7. The Digital Twin simulates the candidates and returns evaluation results.
8. The Main Agent compares the results and selects the final schedule.
9. The selected schedule is passed to the Production Model.
10. The simulated production run updates order progress.
11. The backend persists relevant updates and makes them available to the websites.
12. The customer sees the order as Completed only after execution finishes; actual completion time is then available.

## 4. Machine-health data flow

1. An operator enters readings or requests a synthetic scenario.
2. The health-data component validates and labels the input.
3. Health calculations produce derived values and classifications.
4. The Digital Twin maps relevant health information internally to the simulated equipment.
5. Candidate schedules can be evaluated using the current simulated machine-health condition.
6. Health information and its source are made available to the dashboard.

## 5. CoppeliaSim communication

CoppeliaSim runs locally on the project owner's Windows computer.

A local Python bridge connects to the local CoppeliaSim ZeroMQ Remote API, using the configured local port (initially 23000).

The bridge communicates with the cloud backend through authenticated outbound HTTPS requests or polling.

The ZeroMQ port must never be exposed directly to the public internet.

The cloud backend does not directly connect to the user's local CoppeliaSim instance.

## 6. Database and persistence

One shared Cloud Firestore database is used by the project.

The backend uses Firebase Admin SDK for server-side database operations. Frontend authentication uses Firebase Authentication.

Database collections, document structures, access rules and indexes must be documented in the database documentation.

Private credentials must never be committed to Git.

## 7. Deployment plan

- Three React applications: Firebase Hosting.
- FastAPI backend: Render.
- Persistent application data: Cloud Firestore.
- CoppeliaSim and the Python communication bridge: local Windows computer.

The local bridge must initiate outbound communication to the backend. Do not attempt to expose the local simulation port as a public service.

## 8. Shared integration rules

All components must use agreed shared contracts.

The integration conventions include:

- JSON-based communication.
- ISO 8601 timestamps in UTC.
- Explicit units for physical and time-related values.
- Stable IDs for orders and other entities.
- A schema version for shared payloads.
- Pydantic validation at backend boundaries.
- Documented error responses and failure handling.

The project owner coordinates the final shared contracts and overall integration. Teammate 2 reviews the scheduling-agent interfaces.

## 9. Architecture principle

The agents propose schedules, the Digital Twin evaluates candidates, and the Main Agent makes the final decision.

The Production Model simulates execution of that selected decision.

These responsibilities must remain separate throughout implementation.
